# Garmin Hub — Project Context

- This Week planned-run markers and compliance use the shared `activityMatch.js` helpers; keep their 70% partial-distance threshold named and tested.

## What this is

A personal, single-user web app that ingests my Garmin running data and provides a stats dashboard plus an AI coaching layer. The coach analyses planned-vs-actual training and, in one unified planning mode, can compose individual pace-target sessions or reviewed multi-week adapted plans, then push approved work to Garmin. It can also edit any future workout it can identify on the whole calendar; Runna remains a supported source, not a separate coaching mode.

## Architecture

- **Ingest:** Python + `garminconnect` (0.3.6) + `psycopg` (3). Pulls data, upserts into Postgres. Run by cron.
- **Database:** PostgreSQL (database `garminhub`; locally the Homebrew PG 14 service). `db/schema.pg.sql` is the canonical schema.
- **API:** Node + Express + `pg`, fully async. Two pools mirror a deliberate read/write split (see API section). Serves JSON to the frontend and handles AI-coach calls.
- **Frontend:** React (JavaScript, not TypeScript) + Tailwind + Recharts. Fetch state flows through `useFetch` + the shared `StateWrap` wrapper — every section must render visible loading/error states, never silently fall through to empty data (the hero once rendered a confident fake "rest week" while the API was down).
- **AI layer:** Node calls the Anthropic Claude API (Opus, daily). Uses a separate API key in `.env`.
- **Host:** One Docker Compose project on the DigitalOcean droplet. Caddy reaches the app over `connect-remote_default`; Postgres stays private. The local Mac dashboard and iPhone shell use the same hosted API and dashboard build.

## Data flow

`cron → ingest.py → Postgres ← Express API ← React dashboard`, with the API also calling the Claude API for coaching.

## Database

PostgreSQL, eleven tables (`db/schema.pg.sql` is canonical). Design principle: typed columns for everything with coaching value, plus a `raw_json` **jsonb** column per Garmin-sourced table as a fidelity safety net. Query/chart against typed columns; `raw_json` is the fallback for anything not promoted to a column (and is queryable with jsonb operators). Our own tables (`coach_notes`, `chat_threads`, `profile`, `ingest_state`) have no `raw_json`.

Migrated from SQLite (July 2026) — key facts:

- **Types are real:** all `*_json`/`raw_json` columns are `jsonb` (pg/psycopg return parsed objects — never `JSON.parse` a column value); dates are `timestamp` (`start_time_local`, `lt_detected_date` — local wall-clock, no zone), `date` (`calendar_date` columns, `fetched_at`, `record_date`, `date_range_*`), and `timestamptz` (`created_at`, `updated_at`).
- **String contract preserved:** `server/db.js` overrides the pg type parsers so date/timestamp columns come back as the legacy strings (`YYYY-MM-DD`, `YYYY-MM-DD HH:MM:SS`, ISO-Z) — the API's JSON shapes never changed. Don't remove those parsers casually.
- **BIGINT ids (5):** `activities.activity_id`, `laps.activity_id`, `personal_records.activity_id` (activity ids ~23.5B), `planned_workouts.schedule_id` (negative 60-bit ical hashes) and `planned_workouts.workout_id` all overflow or crowd int4.
- **Two DB roles enforce the read/write split at the database layer:** `garminhub_ro` (SELECT only — the API's read pool) and `garminhub_rw` (DML only, no DDL — the API's write pool + the Python ingest). Connection strings: Node reads `DATABASE_URL_RO` / `DATABASE_URL_RW`, Python ingest reads `DATABASE_URL`, and `PG_ADMIN_URL` is the DDL connection for `ingest/init_db.py` (schema re-apply). Local defaults for all of these are in code; see `db/README.md`.
- First-time setup: `bash db/setup_local.sh` (roles + database + schema, idempotent).

- **`activities`** — one row per completed activity (PK `activity_id`). Run metrics, HR + zones, cadence, power + zones, running dynamics, training load/effect, VO2max, full elevation, calories, geo lat/long for weather backfill, fastest splits. Logic-bearing columns:
  - `activity_type` — raw Garmin `activityType.typeKey` (e.g. `running`, `treadmill_running`).
  - `activity_group` — derived coarse bucket for filtering: any `*running*` → `run`, `soccer`/`football` → `football`, any `*walking*` → `walk`, else `other`. Set by ingest.
- **`laps`** — splits per activity (PK `activity_id` + `lap_index`). Per-lap metrics incl. `intensity_type` (active vs recovery) for matching executed intervals to planned ones.
- **`planned_workouts`** — one row per planned workout (PK `schedule_id` — the Garmin calendar item id, or a **negative** SHA1-hash of the event UID for ical rows, so the two id spaces can't collide). Logic-bearing columns:
  - `source` — `garmin` | `runna_ical` | `app`. Garmin sync covers ~2 weeks with rich step JSON; the Runna ical feed fills in the rest of the plan; `app` rows (Stage 9a) are written by the API at pacer-push time via the write pool — ingest never writes or deletes them (stale cleanup is per-source and only ever runs for `garmin`/`runna_ical`).
  - `plan_id` / `rationale` (Stage 9a) — app rows only: the owning adapted-plan id (NULL = one-off single push) and the per-session "why". App rows use the ical-style negative-hash id space and store the pushed spec verbatim in `steps_json`.
  - `removed_at` (Stage 9d/9f) — soft-delete/tombstone: NULL = live; set = hidden. App rows retain dropped-plan history for 9e load-awareness; `runna_ical` rows may also be tombstoned so an athlete removal stays hidden even if the feed later relists the old date. Every read path filters `removed_at IS NULL`; ingest does not clear tombstones.
  - `is_race_auto` — 0/1, keyword match on title/description for "race"/"parkrun". Owned and overwritten by ingest on every run.
  - `is_race_override` — 0/1 manual override; NULL = none. **Ingest NEVER writes this** — it survives re-ingest.
  - Effective race status = `COALESCE(is_race_override, is_race_auto)`, derived by callers (see the `/api/planned` query).
  - `steps_json` — jsonb. Garmin rows: parsed step/segment structure; ical rows: an array of description-text lines (`parseSteps` in `context.js` passes string arrays through as-is).
- **`plans`** (Stage 9c/9d/9f) — adapted-plan parents, one row per saved plan (PK `plan_id`, text). Holds plan metadata (`name`, `goal_race`, `summary`, `weeks_json`), date span, timestamps, and the forward-only lifecycle `draft → active | queued | discarded`, `queued → active`, `active → completed | archived` (full comments in `schema.pg.sql`). After every session is pushed, a plan becomes `queued` when an unfinished, non-overlapping plan is already active; otherwise the incumbent is retired if needed and the new plan becomes `active`. `GET /api/plan/current` auto-completes finished active plans, then promotes the earliest-starting queued plan when no active remains. At most one plan is active. Plans remain history except athlete-requested draft discard. Draft sessions are dormant; active and queued sessions are live read-path truth. Per-session push state is `planned_workouts.workout_id`. `runna_cleared_at` is the athlete's manual cancel-Runna gate override. No `raw_json`.
- **`recovery`** — one row per `calendar_date` (PK). Consolidates ~7 daily Garmin wellness payloads into one typed row: HRV (+ baseline), resting HR, sleep (stages, score), training readiness (score/level/feedback + factor breakdown), training status, VO2max, all-day stress, body battery. **Training readiness is multi-reading (important):** Garmin takes several readiness snapshots a day, each tagged `inputContext`, newest-first — and it RE-READS after every workout. So `readiness_score` (the array's first element) is the POST-exercise value on any day with a run: an effect of the session, not the state it was started in. Four columns make that legible instead of leaving the coach to assume: `readiness_context` + `readiness_time_local` (which reading the primary score is, and when), and `readiness_wake_score` / `readiness_wake_level` (that day's `AFTER_WAKEUP_RESET` reading — the real pre-training baseline). Backfilled from `raw_json`, which held the full series all along.
- **`coach_notes`** - AI coaching output (PK `id`, identity/auto-generated). `note_type` (`daily`/`weekly`/`ondemand`/`memory`/`debrief`), `content`, `model`, date range. `memory` rows are the coach's **silent persistent memory**: durable athlete facts written via the `remember_fact`/`forget_fact` tools in chat and unified planning, capped at 50, injected into every context build as byte-stable `coach_memory`, and pruned manually in Settings → Coach memory. Writes are deliberately unconfirmed (no approval card) - the one model-initiated DB write in the app. Debrief rows store JSON text with `activity_id` and `debrief` keys so they can link exactly to a run without a schema change. No `raw_json`.
- **`chat_threads`** stores saved chat and planning conversations shared across the Mac dashboard and iPhone app. It holds a server-derived title plus the complete safe client message/UI state in `messages_json`, capped and shape-validated by the API. Its `revision` is an optimistic concurrency token: updates must match the stored revision, so another device's newer turn or deletion cannot be overwritten. Transient requests are not stored as completed actions; restored Garmin-write uncertainty is explicitly blocked from retry. No `raw_json`.
- **`profile`** — single-row (PK `id = 1`, CHECK-enforced) coaching profile. Growable lists stored as jsonb: `shoes_json`, `races_json`, `injuries_json`, `routines_json` (the "other regular activities" — activity/day/intensity, added in 6c), plus `general_notes` — all user-edited via the API's profile endpoints. **Exception:** three lactate-threshold columns — `lt_speed_mps` (LT speed, true m/s), `lt_hr` (LT heart rate, bpm), `lt_detected_date` (source timestamp) — are **ingest-owned** (written by `ingest.py`) and feed the Stage 8 pace system. No `raw_json`.
- **`ingest_state`** — single row (PK `id = 1`, CHECK-enforced) recording the last ingest run: `last_run_at`, `ok`, `summary`. Written by **`ingest.py` itself**, at the end of `main()`, so it covers every path that ingests (both launchd agents, the API's Refresh spawn, a manual terminal run) rather than only refreshes that came through the API. Two readers: the dashboard's "Updated N ago" label and the staleness gate on `POST /api/ingest/refresh`. `last_run_at` is the last COMPLETED attempt, not the last clean one — ingest exits non-zero on any error at all, and a failing pull must not become a retry loop against Garmin; `ok` carries that distinction to the UI. Its write has its own try/except: bookkeeping must never fail a run that actually pulled data. No `raw_json`.
- **`personal_records`** — Garmin-sourced personal bests (one row per record type). Read-only, refreshed by ingest.
- **`race_predictions`** — Garmin's current predicted race times (5K/10K/half/marathon) per `calendar_date`. Read-only, refreshed by ingest.

### Activity-group filtering (important)

Running displays are runs-only. `activity_group` is the filter:

- **Weekly summary / pace trend** — runs only (`activity_group = 'run'`), so walks and football don't pollute mileage and pace.
- **Walks** — ingested for recovery context but excluded from running displays.
- **Football** — shown, but excluded from pace analysis.

## Ingest

`ingest/ingest.py`. Idempotent (safe to re-run from cron): all writes are upserts (`INSERT … ON CONFLICT(pk) DO UPDATE`), no duplicates. Exits **1** when the run collected any errors (even partial, e.g. one rate-limited date) so cron/`daily.sh`/`/api/ingest/refresh` see the failure — note `daily.sh` skips the brief on any non-zero exit.

- **Run/auth:** runs via `/usr/local/bin/python3.13` (Homebrew Python 3.13 — **NOT** Apple's system 3.9). garth token cache lives in `ingest/.garth/` (gitignored), so MFA is only prompted on first login / token expiry. DB connection: `DATABASE_URL` (rw role; local default in code). Per-pull-section transactions: each section commits on success and **rolls back on error**, so one failed pull can't poison the rest.
- **Activities:** pulls the recent N activities (+ laps per activity). Skips the splits fetch when an activity is unchanged and its laps already exist (cheap idempotency win for the common cron case).
- **Planned workouts:** fetched via `get_scheduled_workouts(year, month)` (calendar-based) over a back/forward window (60 days back / 84 days — 12 weeks — forward, matching the coach's `get_scheduled_workouts` tool reach), then `get_scheduled_workout_by_id(id)` for full step detail. Calendar items have mixed `itemType`; planned workouts are `itemType == "workout"`, keyed by date + `workoutId`, with `id` as the schedule id. **Stale-plan cleanup:** after the fetch, future `planned_workouts` rows no longer on the calendar are deleted (a replaced Runna plan leaves no ghosts) — **scoped per-source** (`source = 'garmin'`, so it can never wipe ical rows) and skipped entirely if any month fetch failed, so a transient error can never mass-delete a valid plan. Past rows are never touched.
- **Runna ical feed (full plan):** Garmin only syncs ~2 weeks of Runna; the ical feed exposes the whole plan. If `profile.runna_ical_url` is set (Settings → "Runna calendar feed"), `ingest_runna_ical` fetches it (`icalendar` lib) and maps events over today → +84 days to `planned_workouts` rows with `source = 'runna_ical'` (distance regexed from the title; description lines minus URL lines stored in `steps_json`). **Dedupe:** runs AFTER the Garmin pull — any date a `garmin` row covers is skipped (richer step JSON wins), and the skipped event is deliberately not marked seen so a previously-ingested ical row for that date gets stale-cleaned away. Ical stale cleanup mirrors the Garmin one: per-source, future-only, skipped when the feed fetch fails; if the URL is unset the pull is a no-op (existing ical rows are left alone).
- **Recovery:** pulls ~7 Garmin wellness endpoints per day over a 30-day window. Skips dates already stored **except** the most recent 3 (same-day/recent metrics like sleep and readiness fill in late). Throttled between fetches; on a 429/rate-limit it backs off and retries the date once.

### Race detection (don't trust Garmin's flag)

Garmin's own `race` boolean is unreliable — it's `false` even for workouts titled "10km Race". So we ignore it and derive race status ourselves: ingest sets `is_race_auto` from a keyword match ("race"/"parkrun") on the title/description, and I can manually correct any workout via `is_race_override` (which ingest never touches). Effective status is `COALESCE(is_race_override, is_race_auto)`.

## API

`server/server.js`. **Auth:** the shared `X-Api-Key` gate protects both `/api/*` and every built-dashboard file, so the public hostname returns 401 without `API_SECRET`. The server binds `HOST` with a loopback default; the container sets `0.0.0.0`. CORS allows the two localhost web origins and the iOS shell origin `hub://dashboard` (override via `CORS_ORIGINS`). The iOS shell injects its Keychain value at document start; a local Mac build can use `VITE_API_SECRET`. The hosted build contains no secret. Preflight OPTIONS remains before auth because it cannot carry the custom header. All DB access is **async** (`pg` pools via `server/db.js`): reads use the SELECT-only `garminhub_ro` pool and writes use the DML-only `garminhub_rw` pool. The curated column lists exclude `raw_json` and are awaited before `app.listen`; do not move that init after routes can fire. The narrowly scoped DB writes:

- `POST /api/planned/:schedule_id/race-override` — body `{ override }` where override is `1` (force race), `0` (force not-race), or `null` (revert to auto). Writes **only** `is_race_override`.
- `POST /api/profile` — replaces the single `profile` row (shoes/races/injuries/routines/notes/runna_ical_url). `GET /api/profile` returns parsed arrays.
- `POST /api/coach/daily` — generates the glance brief and inserts a `daily` row into `coach_notes`.
- `POST /api/plan/save` — persists a reviewed adapted plan (Stage 9b/9c): re-runs the Python guard on the exact specs being written, then ONE atomic statement (CTE chain: delete prior plan rows on the new plan's date span → prune parents left with no sessions → insert the `plans` parent → multi-row session insert) writing `source='app'` rows sharing a fresh `plan_id`. DB write only — no Garmin. One-off pushed sessions (`plan_id` NULL) are never deleted by a re-save; a span whose plan rows are already partly pushed to Garmin is **refused (409)** — replacing a live plan is re-adaptation (9d), which owns unscheduling.
- `POST /api/plan/:plan_id/push-next` — activation core: pushes the oldest future pending session to Garmin, records the returned `workout_id`, and returns progress. Once none remain, activation retires an already-finished incumbent as `completed` or an overlapping unfinished incumbent as `archived`, then marks the incoming plan `active`; an unfinished non-overlapping incumbent remains active and the incoming plan becomes `queued`. Retirement is written before the incoming flip. The client loops sequentially under the shared plan lock; Garmin-succeeded-but-record-failed returns `recorded:false` so a blind retry cannot double-book.

- `POST /api/plan/:plan_id/runna-cleared` — 9d-3 manual cancel-gate override: the athlete asserts Runna is cancelled ("Runna's already gone — skip this check"). Stamps `plans.runna_cleared_at` and, on that assertion, deletes future `runna_ical` rows (pure feed mirror — if the feed is actually still alive they reappear on the next ingest, cosmetically, with the gate already satisfied; if the feed died with the cancellation, ingest's deliberately conservative stale cleanup would otherwise never clear them). `garmin` rows are left to ingest's calendar-driven cleanup — they may be real workouts. Draft/active plans only (409 otherwise). The athlete can see their own Runna app; a feed check can never hold activation hostage.

- `POST /api/plan/:plan_id/discard` — 9d-2 draft discard: hard-deletes a `status='draft'` plan and its session rows in one atomic CTE statement (writeDb), gate re-checked inside it. Refused (409) for any other status and for a mid-activation draft (any session carrying a `workout_id` — deleting those would orphan live Garmin workouts); 404 for an unknown plan. Chat-invoked via the planning coach's `{"edit": "discard_plan", "plan_id"}` directive, athlete-confirmed in the UI (same confirm-card flow as the 9d edits); shares the push-next in-process lock so a discard can't race an in-flight activation push.

- `POST /api/plan/session/:schedule_id/move` / `.../remove` / `.../replace` — Stage 9f whole-calendar future editing. `schedule_id` addresses any visible future `app`, `garmin`, or `runna_ical` row, not only an active plan. All three use `pacer_cli.py reconcile` plus source-aware bookkeeping. App edits retain their buildable spec and plan history; Garmin rows can also move/remove, and can be replaced when the coach supplies a new buildable spec; Runna-feed-only rows are remove-only. Optional `workout_id`/`schedule_id` inputs let reconcile unschedule directly; otherwise it uses the legacy lookup. Move schedules first then unschedules the old occurrence; replace uploads/schedules first then unschedules; remove only unschedules. Runna feed removals leave a `removed_at` tombstone. Collisions require an explicit forced retry, and Garmin-then-DB failures return `recorded:false`.

The AI-coach and pacer routes also spawn Python or call Claude (see AI coach / Pacer below); `POST /api/pacer/push`, `POST /api/plan/:plan_id/push-next` (both through `pacer_cli.py push`) and the three Stage 9d session-edit endpoints (through `pacer_cli.py reconcile`) are the only endpoints that write to **Garmin**. `POST /api/ingest/refresh` spawns `ingest.py` on demand (in-process lock stops concurrent runs).

**Prompt-cache stability (real money):** `buildContext` / `buildPlanningContext` output is injected as a `cache_control`'d system block on every coach call, so it must be **byte-stable across calls** — a per-call timestamp in it busts the cache every request. That's why the context carries a day-granular `today` (the coach needs it to resolve "Saturday" to a date), not an ISO timestamp; never add per-call values (timestamps, randomness) to those payloads. `renderContextDump` stamps its timestamp at render time, outside any cached path.

Read endpoints: `/api/health`, `/api/activities` (+ `/:id` with laps), `/api/planned` (date-scoped app/Garmin mirror dedupe, future Garmin detail overlay, app-plan precedence, then same-day race collapse), `/api/plan/current` (auto-completes an ended active plan, promotes the earliest-starting queued plan if no active remains, then selects active > queued > newest draft > newest completed; a quiescent active may yield the card to a newer draft), `/api/recovery`, `/api/summary/weekly`, `/api/training-balance`, `/api/personal-records`, `/api/race-predictions`, `/api/coach/context` + `/api/coach/context-dump`, `/api/coach/notes`.

## Known Garmin data shapes (already inspected)

- **Activities:** ~99 fields per run; curated subset promoted to columns, rest in `raw_json`.
- **Laps/splits:** per-lap metrics incl. `intensityType` (active vs recovery).
- **Workout step structure:** segments → steps; repeats are `RepeatGroupDTO` with `numberOfIterations` + child steps. Pace targets use `targetType: "pace.zone"` with `targetValueOne`/`targetValueTwo` as speed in m/s (higher = faster bound).

## Pacer / Engo 3 constraint (CRITICAL for Stage 5)

Generated pacing workouts **MUST** be split into 500m segments. The Engo glasses average pace over the whole step, so a longer step gives too wide a sample and ruins the pacing display. So: distance ÷ 500m = step count (5k → 10 steps, 10k → 20 steps).

- Support **per-segment** pace targets (not one repeated pace) so negative-split strategies are possible.
- Encoding: `targetType: "pace.zone"`, `targetValueOne`/`targetValueTwo` as m/s bounds.
- The existing "Sub 20 5k" planned workout is the canonical template.

## Conventions & preferences

- Keep all files as brief and lean as possible. No over-engineering, no speculative abstraction.
- Agree approach before writing; I QA each stage before moving on.
- Credentials and API keys live in `.env` (gitignored), read via environment variables. Never hardcode secrets.
- Ingest must be idempotent — safe to re-run (upserts, no duplicates) since it runs on a cron.

## Build & deploy

Production is `deploy/droplet/`: one Node and Python 3.13 image plus private
Postgres, reached only through edge Caddy. Host cron runs ingest plus capped
debrief generation every two hours, the daily brief at 10:00 Europe/London,
the weekly review on Sunday at 19:00, and a retained nightly `pg_dump`. Follow
the runbook for first deploy, data migration, updates, rollback, and restore.
Cron jobs publish atomic JSON results from `deploy/droplet/job-status`, mounted
read-only into the app for `/api/status`. Hosted Mac mode also installs the
daily `com.garminhub.offsite` pull, which retains private local snapshots for
30 days and reports its result through `jobs.sh mark offsite`.

The iPhone project is generated from `ios/project.yml`. Its `hub://dashboard`
scheme proxies the dashboard, assets, and API to the droplet with the Keychain
API key on every request. External links leave the shell and receive no key.

### Local macOS

Local always-on test deployment via launchd (`deploy/local-macos/`, see its `README.md`). **This trips people up:**

- **Frontend changes don't hot-reload.** The web service runs `vite preview` serving the **production build** (`web/dist`) on `:4173` — not a dev server. To see any frontend change you must rebuild: `bash deploy/local-macos/install.sh` (it stops stray dev servers, runs `npm run build`, and reloads the launchd services).
- **API changes need a service restart.** After editing `server/`, restart the API launchd agent: `launchctl kickstart -k gui/$(id -u)/com.garminhub.api` (it serves on `:3001`, loopback only — nothing on the LAN, e.g. a phone, can reach it).
- **The API secret spans both deploy halves.** `API_SECRET` (`server/.env`) and `VITE_API_SECRET` (`web/.env.local`, gitignored) must hold the same value — the frontend bakes it into the built bundle, so rotating it = edit both files **and** rerun `install.sh` (a stale bundle 401s on everything). If `API_SECRET` is missing the server exits at startup, which under launchd `KeepAlive` looks like a crash-loop in `garmin-hub-api.log` — never a running-but-open API.
- **Ingest runs on TWO schedules, and the dashboard refreshes itself.** Before this, the only automatic ingest was the 10:00 daily one, so a run logged at midday did not reach the dashboard until the next morning — and a stale dashboard looked identical to a current one. Three layers now:
  - `com.garminhub.ingest` runs `daily.sh --no-insight` **every 2 hours** (`StartInterval`, so launchd coalesces intervals missed while asleep into one run at wake). Ingest only — the brief stays a once-a-day artefact because it spends Claude credit. The periodic agent shares `daily.sh` rather than copying it; the flag is what suppresses the insight step.
  - **The dashboard refreshes on open and on every return to the tab** (`RefreshButton`, `App.jsx`) — gated server-side, so only genuinely stale data costs a Garmin pull.
  - `POST /api/ingest/refresh` takes an optional `max_age_minutes`: if `ingest_state.last_run_at` is younger it returns `{ ok: true, skipped: true, … }` **without spawning**, so a reload or a second tab is free. The manual Refresh button sends no window and so always pulls. A 409 (`ingestRunning`) now carries the current state along with it, and the automatic caller treats it as an expected outcome rather than an error. Threshold lives in the frontend (`AUTO_REFRESH_AFTER_MIN`, 30 min).
  - The topbar shows **"Updated N ago"**, ambering past 24h or when the last run reported errors. Silent staleness was the actual bug; the label is what makes it visible.
- **The daily brief IS generated on a schedule.** `com.garminhub.daily` runs `deploy/local-macos/daily.sh` at **10:00 local** — it ingests, then (on success) POSTs `/api/coach/daily` to generate and persist the day's brief. The dashboard's **Regenerate** button generates the same brief on demand; they are not mutually exclusive. (Ingest can also be triggered mid-day via the Refresh button → `POST /api/ingest/refresh`.) Failure semantics: ingest exiting non-zero (now: any error at all) skips the brief, and the brief call uses `curl --fail-with-body` — an HTTP 500 fails the run (script exits 1) while still logging the error body.

## Known rough edges (consolidate later)

- **Known edge - timeout between upload and schedule.** If the pacer process is killed after upload but before scheduling, Garmin may retain an unscheduled workout in the library; retry adoption can only identify scheduled workouts.

- **Coach honesty contract and trap eval.** Chat, day insights, the detailed report, and planning share one rule: verify athlete claims against the data, lead with an independent assessment and numbers, disagree plainly, separate evidence from judgement, state confidence, and surface material risks. The brief carries the compact version. `node server/eval/coach-traps.mjs --dry-run` validates and builds the 15 fixture requests without an API call. A live run needs `ANTHROPIC_API_KEY`; `--coach /path/to/server/coach.js` runs the same cases against another checkout for a baseline. Never print the key or run the live eval without approval.

- **Coach evidence and principles.** Chat, day insights, detailed reports, and planning share `COACHING_PRINCIPLES`, including illness safety, intensity balance, conservative progression, tapering, trend-based recovery judgement, back-to-back quality, and exact date plus weekday quoting. The cached context includes Garmin recovery load fields, the real ACWR ratio and status parsed through the shared training-balance helper, the separately labelled Garmin ACWR readiness factor score, plus derived 42-day CTL, 7-day ATL, TSB, and an eight-week trend warmed from 365 days of load. `get_training_history` supplies weekly volume, HR-zone intensity, comparable-HR easy-run efficiency with sample counts, approximate steady-run decoupling, load, and races; `get_plan_compliance` applies calendar precedence and race dedupe before same-day nearest-distance matching with the week strip's 70% partial threshold. Both tools use the read pool and return compact method-labelled text.

- **Migrations:** `db/schema.pg.sql` is canonical, applied via `CREATE TABLE IF NOT EXISTS` (`db/setup_local.sh` / `ingest/init_db.py`) — so it **cannot alter existing tables**. A schema change to an existing table = an `ALTER TABLE` run against the live DB **plus** the matching edit to `schema.pg.sql` (so fresh setups agree). The SQLite-era one-script-per-change `migrate_*.py` files are retired to `attic/`. Still no formal migration tool; adopt one if schema churn picks up.

- **Readiness is post-exercise on run days (fixed, don't regress it).** The coach used to read a run day's readiness as the state the athlete set out in — "readiness 27 and you still ran 16km", when they had actually woken at 94 and the 27 was the run's own cost. Across 81 days of history the score dropped on 35 of them by an average of 28 points (max 67), so this misread a third of all training days. Fixed at three layers: the schema/ingest columns above (plus a one-off `UPDATE` backfill from `raw_json`); `recoverySnapshot` (`context.js`) now emits `readiness_measured` (`on_waking` / `after_exercise` / `during_day` / null) and `readiness_on_waking` alongside the score, so today's context AND `sectionAlignedRecovery`'s `recovery_on_day` are both self-labelling; and a shared `READINESS_RULES` fragment in `coach.js` carried by chat, day-completed, detailed-report and planning prompts (the brief gets a one-line version). `get_activity_detail` is the exact form: it reads the timestamped series straight out of `raw_json` and reports the readings immediately BEFORE and AFTER that specific activity, which also resolves double days (the evening run's "before" is the morning run's post-exercise reset). HRV, resting HR and sleep are overnight measurements and so genuinely pre-run — they never needed this treatment.
